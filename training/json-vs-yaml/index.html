JSON vs YAML: when the extra syntax pays for itself

YAML is a superset of JSON with comments, anchors and implicit typing. That last one is why a config file can turn the string "no" into a boolean. A practical comparison.

Short answer: use JSON for data that machines exchange, YAML for configuration that humans edit. JSON’s grammar is tiny and unambiguous; YAML’s is larger and its implicit typing is a recurring source of surprises.

The syntax difference, briefly

{
  "name": "api",
  "replicas": 3,
  "env": ["prod", "eu"],
  "resources": { "cpu": "500m", "memory": "512Mi" }
}
name: api
replicas: 3
env:
  - prod
  - eu
resources:
  cpu: 500m
  memory: 512Mi

The YAML version is shorter and, for many people, easier to scan. It also has comments, multi-line strings, anchors and aliases — features that matter when a human maintains the file by hand.

What you pay for the brevity

Implicit typing. In YAML 1.1, no is a boolean. In YAML 1.2 core schema it is a string. Which one you get depends on the parser version, which depends on the language and library. A country code NO (Norway) has been parsed as false in production systems more than once.

Whitespace significance. Indentation defines structure. A tab where a space was expected is a parse error at best, a silently different tree at worst.

The Norway problem’s cousins. Sexagesimal numbers (12:30 as 750), octal-looking values with a leading zero, and dates that become Date objects in some parsers.

Multiple documents. A single YAML file can contain several documents separated by ---. Tools that assume one document silently ignore the rest.

Anchors and aliases. Genuinely useful for repetition, and genuinely confusing when the resulting object graph has cycles or shared references that JSON cannot express.

What conversion loses

Converting YAML to JSON is lossy in specific, predictable ways:

  • Comments disappear. JSON has nowhere to put them.
  • Anchors are expanded. The alias becomes a full copy, which is semantically equivalent and textually larger.
  • Type information can shift. A value the YAML parser resolved as a boolean becomes a JSON boolean; a value it resolved as a string stays a string. The conversion makes that decision visible, which is useful — but it is a decision the parser already made.
  • Multiple documents collapse. Only the first document survives in a single JSON value.

Converting JSON to YAML is safer, because JSON’s type system is a subset. The risk is in the reader: a YAML parser that resolves types differently may read back something other than what you meant. Quoting strings that look like booleans or numbers avoids it, and a good converter does that automatically.

Choosing

SituationFormat
API request or response bodyJSON
Config a human edits by handYAML, with explicit quoting for ambiguous strings
Machine-generated config (CI pipelines)Either; JSON avoids the typing surprises
Data with comments that matterYAML
Interchange between languagesJSON
Very large documentsJSON — parsers are faster and streaming support is broader

The pattern is consistent: JSON for transport, YAML for authorship. Kubernetes chose YAML and pays for it with a validator ecosystem; most APIs choose JSON and pay for it with no comments.

Converting safely

The JSON ↔ YAML converter parses with a real YAML 1.2 parser rather than transforming text, reports when a file contains multiple documents, and preserves quoting where a string would otherwise change type. It does not invent comments on the way back — there is nowhere to put them.

FAQ

Is JSON valid YAML? YAML 1.2 is a superset of JSON, so yes — with the caveat that some parsers in the wild are still 1.1.

Why did my on: key become true:? YAML 1.1 treats on as a boolean. Quote it, or use a 1.2 parser.

Can YAML represent anything JSON cannot? Yes: comments, anchors, multiple documents, and non-string mapping keys.

Which is faster to parse? JSON, by a wide margin. YAML parsing involves more work per token.

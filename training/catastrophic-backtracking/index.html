Catastrophic backtracking: how a regex freezes a tab

Nested quantifiers turn a short string into an exponential number of paths. Why the browser hangs, how to spot the pattern, and how to test a regex without locking up the page.

Editorial Team · 10 September 2026 · 3 min read

Short answer: a pattern like (a+)+$ has exponentially many ways to match a failing string. The engine tries all of them before giving up. On a 30-character input that is billions of steps, and the thread never returns — which is why the tab, not just the regex, appears to die.

The mechanism

Most JavaScript engines use a backtracking matcher. It walks the pattern left to right, and when a choice point fails, it returns to the most recent choice and tries the next option. For (a+)+ against aaaa...b, each a can belong to the inner group in many different combinations, and the trailing b can never match, so the engine enumerates every combination before concluding failure.

The cost is exponential in the length of the input. That is the whole story: a 20-character string might take milliseconds, a 30-character one takes minutes, and a 40-character one takes longer than the universe has existed.

The shapes to look for

  • Nested quantifiers on the same class: (a+)+, (\w*)*, (a|aa)+.
  • Overlapping alternations inside a repeat: (a|ab)+.
  • A quantifier followed by an optional that can also match: .*.*= on a long line.
  • Unanchored search with a failing suffix: the engine retries from every start position.

A single one of these is not automatically a bug — (a+)+ on aaaa succeeds quickly. It becomes a denial-of-service vector when the input is attacker-controlled and can be made to fail.

Testing without locking up the page

A regex tester that runs the pattern on the main thread inherits the problem: one bad pattern and the whole page freezes, including the button you would use to stop it. The only reliable mitigation is to run the match somewhere that can be killed.

A Web Worker is that place. The pattern runs in a separate thread; the main thread starts a timer; if the timer fires first, the worker is terminated and the UI reports a timeout. That is what this site’s Regex Tester does, with a 900 ms budget.

const worker = new Worker(URL.createObjectURL(new Blob([source], { type: "text/javascript" })));
const timer = setTimeout(() => worker.terminate(), 900);

Two caveats worth stating: a terminated worker tells you nothing about why the pattern failed, and the same pattern in your production code has no such guard unless you add one.

Rewriting the pattern

The fix is almost always to remove the ambiguity rather than to add a timeout:

DangerousSaferWhy
(a+)+$a+$The outer group adds nothing but choice points
(\w*)*\w*Same
(a|aa)+a+The alternation is redundant
.*.*=[^=]*=One quantified class, no ambiguity

For parsing structured text, a proper parser is usually the right answer. Regex is excellent at “does this string have this shape” and poor at “parse this nested document”.

When it is not your pattern

Third-party validation libraries and WAF rules can carry vulnerable patterns. If a request hangs in production and the stack shows a regex, the pattern may not be in your code — it may be in a schema validator or a router.

FAQ

Is this the same as ReDoS? Yes — ReDoS is the denial-of-service attack that exploits catastrophic backtracking.

Do all engines backtrack? No. RE2 and similar engines guarantee linear time by giving up backreferences and lookarounds. JavaScript’s engine does not offer that mode.

Does a timeout fix the vulnerability? It limits the damage in that one place. The pattern is still wrong and should be rewritten.

Why does my pattern work on short input? Because the cost is exponential in length. Short inputs hide the problem completely.

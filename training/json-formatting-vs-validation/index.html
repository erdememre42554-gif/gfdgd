Formatting vs validating JSON: they are not the same operation

A formatter that silently repairs invalid JSON is worse than useless. What validation actually checks, where parse errors point, and why duplicate keys are a trap.

Short answer: formatting changes whitespace; validation decides whether the document is JSON at all. A tool that reformats something it could not parse is guessing, and guessing about data is how production bugs get shipped.

The grammar is small and strict

RFC 8259 defines JSON with six value types and a handful of structural rules. There are no comments, no trailing commas, no unquoted keys, no single quotes, and no undefined. A parser that accepts those is not parsing JSON; it is parsing something adjacent, which is fine for a config file format and wrong for an API payload.

That strictness is the point. If a document validates against the grammar, any conforming parser anywhere will read it the same way. If it only validates against your editor’s lenient mode, you have learned nothing about the other side.

Where a parse error actually points

JSON.parse throws a SyntaxError whose message includes a position. That position is where the parser gave up, which is often one token after the real mistake.

Three common patterns:

  • A trailing comma. The parser reads the comma, expects another member, finds }. The error points at the closing brace; the mistake is the comma before it.
  • A missing closing brace. The parser keeps consuming until the input ends, so the error points at the end of the document rather than at the object that was never closed.
  • An unquoted key. The error lands on the first character of the key, which is at least close to the real problem.

A formatter that shows line and column converts that offset into something you can navigate to. It does not fix the document, and it should not pretend to.

Duplicate keys: valid JSON, undefined behaviour

RFC 8259 says object names should be unique, and that when they are not, the behaviour is unpredictable across implementations. JavaScript’s JSON.parse resolves this by keeping the last value.

{"role": "user", "role": "admin"}

This parses. JSON.parse returns { role: "admin" }. Nothing warns you. If the duplicate came from a merge bug, you now have a privilege escalation that looks like a well-formed document.

Detecting duplicates requires a parser that reports them, which the standard JSON.parse does not do. The honest options are a custom parser or a lint step — a formatter cannot help, because by the time it sees the value the duplicate is gone.

Numbers are doubles

JSON numbers are not integers, decimals or bigints. They are IEEE-754 doubles in every mainstream implementation. Consequences:

  • Integers beyond 2^53 cannot be represented exactly. A Discord snowflake or a database bigint will silently change value if parsed as a number.
  • 1.0 and 1 are the same value after parsing, so a formatter may normalise one to the other.
  • Very large exponents round.

If a payload carries 64-bit identifiers, the correct fix is at the producer: send them as strings. No client-side tool can undo a precision loss that happened during parsing.

What a good formatter does

  1. Parses strictly, and reports the failure with a position.
  2. Never rewrites invalid input into something that looks valid.
  3. Makes the transformation explicit — indentation width, key sorting — and labels the destructive ones.
  4. Shows you the structure, not just the text: node count, depth, the widest array.

Sorting keys is worth calling out. It changes the document’s order, which matters for signatures, byte-level diffs and anything relying on insertion order. The option exists, and it is labelled as order-changing.

FAQ

Can I validate JSON without parsing it? You can write a validating parser, but you cannot avoid parsing — validation is parsing, minus the object construction.

Is JSON5 valid JSON? No. It is a superset with comments, trailing commas and other conveniences.

Why does my editor accept comments? Because it parses JSONC or JSON5 for configuration files. That is a deliberate, documented leniency, not evidence that the payload is valid.

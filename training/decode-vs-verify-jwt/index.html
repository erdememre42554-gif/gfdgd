Decoding a JWT is not verifying it

A JWT's claims are Base64URL-encoded, not encrypted, and anyone can write any claim into a token. What decoding shows, what verification requires, and why alg: none is a red flag.

Short answer: decoding turns the token back into readable JSON. Verification checks that the signature was produced by the holder of a key. The first requires nothing; the second requires the issuer’s public key or shared secret, which a client-side tool does not have unless you supply it.

What the three segments are

A signed JWT (JWS, RFC 7515) has three Base64URL segments separated by dots:

header.payload.signature
  • Header — JSON describing the algorithm (alg) and key id (kid).
  • Payload — JSON claims: sub, iss, aud, exp, iat, and whatever else the issuer added.
  • Signature — the output of signing base64url(header) + "." + base64url(payload) with the issuer’s key.

The first two are readable by anyone holding the token. That is by design: they are encoded, not encrypted. If you put a credit card number in a claim, you have published it to every proxy, log and browser that sees the token.

What verification actually does

Verification takes the header, the payload, the signature and a key, and asks: does this signature validate for this exact input?

That requires:

  1. The right key — the issuer’s public key (RS256/ES256) or the shared secret (HS256).
  2. A key selection strategy — usually the kid in the header matched against a JWKS endpoint.
  3. Algorithm pinning — the verifier must accept only the algorithm it expects, not whatever the header says.

Point 3 is where implementations break. If a verifier reads alg from the token and trusts it, an attacker can change RS256 to HS256 and sign with the public key as if it were an HMAC secret. The fix is to configure the expected algorithm and reject anything else — never let the token choose.

Why this tool does not verify

Because verification needs a key, and a tool that silently “verifies” without one would have to either:

  • skip the check and say “valid” (dangerous), or
  • fail always, which is useless.

So the tool decodes, shows the claims, converts timestamps, and states plainly that the signature is unexamined. If you have the key, verifying is a few lines of Web Crypto in your own application — where the trust decision belongs.

Reading the claims

The registered claims that matter in practice:

ClaimMeaningCommon bug
expExpiry, seconds since epochIssued with a lifetime of seconds instead of hours
nbfNot valid beforeClock skew makes a fresh token unusable
iatIssued atUsed for “token age” checks that assume a synced clock
audIntended audienceVerifier does not check it, so a token for service A works on service B
issIssuerNot checked against an allow-list

exp, nbf and iat are NumericDate values: seconds, not milliseconds. Multiplying by 1000 for Date is the only conversion needed, and forgetting it is the single most common JWT bug — a token that “expires in 1970”.

alg: none and other red flags

An unsigned token has "alg": "none" and an empty signature segment. It is a legitimate part of the specification for cases where the token’s integrity is guaranteed by another channel. In practice, a verifier that accepts it is broken, and attackers know it.

Other things worth noticing in a header: an unexpected kid, a jku/x5u pointing at an attacker-controlled URL, or an algorithm that does not match the issuer’s documented configuration.

FAQ

Can I trust the sub claim after decoding? Only after verification. Before that, it is a string someone typed.

Is a JWT encrypted? Not unless it is a JWE (five segments). A JWS is signed, not encrypted.

Why is the token so long? Base64URL adds about a third, and claims are verbose. Long tokens in URLs hit header and URL-length limits.

Does an expired token still decode? Yes. Expiry is a claim, not a property of the encoding.

Six JSON parse errors you will actually hit

Trailing commas, unquoted keys, single quotes, NaN, control characters and BOM. What each one looks like, why the parser rejects it, and the fix that does not involve a lenient parser.

Short answer: most parse errors are one character. The parser tells you where it stopped; the fix is almost always a few characters earlier. Below are the six that account for most real-world failures.

1. The trailing comma

{"a": 1, "b": 2,}

Valid in JavaScript object literals, invalid in JSON. The parser reads the comma, expects another member, and finds }. The error points at the brace; the comma is the culprit.

This is the most common failure because it is invisible in a diff and easy to introduce by hand-editing a formatted document.

2. Single quotes

{'a': 1}

JSON strings must use double quotes. Single quotes are a Python/JavaScript habit that no conforming parser accepts.

3. Unquoted keys

{a: 1}

Keys are strings, and strings are quoted. Some serialisers will happily emit this if you hand them a JavaScript object string; the receiver will reject it.

4. NaN, Infinity and undefined

None of these exist in JSON. A number is a decimal literal; there is no representation for “not a number” or infinity. Serialisers in JavaScript convert NaN to null silently, which is how a numeric field becomes null in an API response and nobody notices for a week.

If you need to express these, use a string ("NaN") or omit the field, and document which convention the consumer should expect.

5. Raw control characters in strings

A literal newline inside a string is invalid:

{"note": "line one
line two"}

It must be escaped as \n. The same applies to tabs and to any character below U+0020. This usually appears when someone builds JSON by concatenating strings instead of serialising an object.

6. A byte-order mark

A UTF-8 BOM (EF BB BF) at the start of a file is invisible in most editors and rejected by strict parsers, because the grammar expects { or [ as the first significant character.

The fix is at the producer: write UTF-8 without a BOM. If you only control the consumer, strip \uFEFF before parsing — and note that you are now parsing something slightly different from what the file contains.

Reading the error message properly

A JavaScript parse error looks like this:

Unexpected token } in JSON at position 412

position 412 is a byte offset into the string. Converting it to a line and column is the single most useful thing a formatter can do, because the eye can jump to a line but not to offset 412.

Two habits make debugging faster:

  • Look one token back. The parser stops where it cannot continue, which is usually just after the mistake.
  • Check the end of the document first. “Unexpected end of JSON input” almost always means an unclosed bracket somewhere above.

What not to do

Do not switch to a lenient parser to “make it work”. eval, JSON5 and auto-repair libraries all accept documents that other systems will reject. You have moved the failure from your machine to a consumer’s machine, where it is more expensive.

Validate strictly where the data enters, and fix it at the source.

FAQ

Is {"a": 1,} valid in any JSON dialect? JSON5 and JSONC accept it; RFC 8259 does not.

Why does my payload parse in Python but not in JavaScript? Python’s json module is also strict about these rules; the difference is usually that one side already normalised the value.

Can a formatter fix a BOM? It can strip it if it is written to, but that is a repair. Better to remove it at the producer.
